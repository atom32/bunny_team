# Neon Bastion：功能盘点与 Demo 缺口

## 2026-09-30：P0 恢复流程与共享渲染更新

这一轮已修复下列卡死路径，以下旧版审查保留为历史记录：

| 情况 | 当前行为 |
|---|---|
| 坏 JSON、非法字段类型、无效版本/物品/负重数据 | 不再让 Profile 为空；提供重试原档、恢复有效备份、归档坏档并重新开始、退出 |
| 保存中断/磁盘不可写 | 临时文件校验后替换，保留上一份有效 `.bak`；失败保留原档、内存进度和待结算 Session，可重试或明确选择不保存继续 |
| 弹药库存过多、超重、Session 创建失败 | 配装预览实际携带重量；每武器以约三弹匣为目标携带完整弹药堆叠，其余留仓库；错误可见，Operations 不再提前隐藏，重复点击不替换现有 Session |
| 弹匣重复生弹药、装满背包后不能撤离 | 初始装弹从携行库存扣除，弹匣余弹计入重量，回收全部弹匣先模拟再整体提交；满仓库扩容接收回收物，不丢收益 |
| Esc / Pause / Resume | 开场跳过、设置返回、搜刮关闭优先；其他场景打开统一菜单。暂停冻结移动、AI、射击预警计时和游戏时间；清空积压开火输入，失焦暂停当前战斗 |
| 放弃 / 返回基地 / 主菜单 / Quit / 窗口关闭 | 活跃任务先确认；放弃只丢本次进度与拾取物，保留出击前仓库。正常结算先成功保存再发布数据；失败能重试。过场中的退出请求等过场结束后处理 |
| Continue / 继续游戏 | 暂停菜单继续原战斗；主菜单 Continue 恢复已保存仓库和配装、进入基地。尚未实现跨进程恢复半途战斗 |
| 场景缺失、结算页没有 Session | 可操作的恢复/退出入口，不留下无按钮的空场景；已完成提交后导航重试不会再次发放物品 |

渲染从桌面 GL Compatibility 改为 **Forward+ + 4× MSAA**；基地、战场、结算共用 AgX 色调映射、中性环境反射、轻量 SSAO 与发光阈值。灯光减轻皮肤/头发高光溢出。临时 Artoria 的脸型、烘焙贴图和原始 Blender 文件保持不变；脸部腮红、毛发材质和 Blender 节点转游戏材质的差距仍是资产层问题，不能承诺换渲染器就等同 Blender。Compatibility 可以通过启动参数回退。实现与参数见 `scripts/systems/render_profile.gd`，能力边界参见 [Godot 渲染器文档](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html) 和 [Environment 文档](https://docs.godotengine.org/en/stable/classes/class_environment.html)。

验证：冷导入 0 错误/0 警告，37/37 场景测试、5 条真实进程退出路径、Forward+ 图形路线 13 项检查通过。Main 强制 headless 退出仍有既有的 2 ObjectDB 实例警告，无脚本错误。M5 上 90 帧战斗样本中位数 16.708 ms / p95 18.217 ms；这是短时采样，不是全平台性能认证。验证与截图归档：[机器报告](p0_verification/verification.json)、[暂停](p0_verification/presentation/05_pause_battle.png)、[坏档恢复](p0_verification/presentation/09_save_recovery.png)、[渲染后的基地](p0_verification/presentation/02_loadout.png)。所有测试都使用隔离项目/存档，不触碰玩家正式存档。测试不等于陌生玩家完整首玩验收；引导、任务奖励、护甲价值、关卡节奏等内容缺口仍待后续处理。

## 本轮复现的具体问题

以下探针均在独立副本、独立存档目录运行，没有修改正式游戏代码或个人存档。完整结果见 [审查验证记录](demo_audit_2026-09-28.json)。

### 1. 坏存档会导致主入口连续脚本错误（优先修复）

复现：在隔离目录写入无法解析的 `profile.json`，再以正常主入口启动。`ProfileRuntime` 读取失败后仍保留空 profile；Hanger 初始化中止，Hideout 随后对空 `hanger_ui`、空 camera 调用方法，出现连续错误。

定位：[profile_runtime.gd](../scripts/systems/profile_runtime.gd) 的 `_ready/load_profile`；[hideout.gd](../scripts/presentation/slice/hideout.gd) 的 `_ready/_process`。

建议：提供明确的读档失败页面、保留原文件、选择恢复备份或新建；采用临时文件替换和备份。失败不能进入依赖完整 profile 的场景。

### 2. 弹药库存过多会导致出战失败，并把基地界面隐藏（优先修复）

复现：在合法新档仓库增加 10,000 发普通弹药，仓库容量与数据验证仍通过；出战自动携带所有匹配弹药，超过 100 kg 携行限制。Session 创建失败，Operations 的确认按钮已先执行 `ui.hide()`，没有恢复界面。

这是高库存边界探针，不表示首局默认库存就会触发。日常体验也缺少弹药数量选择和出战失败提示。

定位：[hanger.gd](../scripts/hanger/hanger.gd) 的 `_get_carried_ammo_ids/_on_deploy_requested`；[hideout.gd](../scripts/presentation/slice/hideout.gd) 的 `_deploy`。

建议：出战选择携行数量、显示预估重量；无弹/超重等情况给出可修正提示；确认成功后再隐藏页面，失败恢复操作。

### 3. 不开枪直接撤离，可以增加仓库弹药（经济规则需要收口）

复现：默认 AR + Rocket，新档备弹 120 发普通弹药、4 发火箭；开启 Session 后不射击、不搜刮，直接完成撤离和结算。仓库变为 **150 发普通弹药、5 发火箭**。

原因：初始弹匣直接填满，没有从携行库存扣除；撤离又把弹匣余弹转回库存。该行为有现有测试显式维护，属于早期原型规则，不能说成这次 pull 引入的回归。

定位：[sortie_session.gd](../scripts/data/sortie_session.gd) 的 `_initialize_weapon_runtime_state/finalize_runtime_ammo`；[ammo_runtime_test.gd](../tests/ammo_runtime_test.gd)。

建议：统一“仓库 → 携行 → 弹匣 → 回收”的总量守恒。若确实需要免费出击补给，给它独立、清晰且不能反复变现的规则。

### 4. 轻甲与重甲承受同样伤害（配装价值需要落地）

复现：分别穿轻甲、重甲，接收相同 25 点伤害包，两次均扣 **25 HP**。重甲说明写“以速度换防护”，实际只增加重量并降低移速，受伤路径不读取护甲防护属性。

定位：[player_controller.gd](../scripts/player/player_controller.gd) 的 `receive_damage`；[heavy_armor.tres](../resources/equipment/heavy_armor.tres)。

建议：实现可感知的轻/重甲取舍，并在配装界面显示速度、防护和容量差异。背包效果也应有明确数据说明。

## 建议下一轮做一个有限范围的里程碑

**里程碑 A：陌生玩家能顺利完成一局。** 先修坏档/失败出战恢复，补暂停和基础引导，缩小 HUD，明确目标方向。沿现有地图设计一条稳定路线；北部无玩法区域可以暂不纳入引导路线。

**里程碑 B：第二局有意义。** 确定弹药和死亡规则，补真实的护甲差异、携行选择、一次任务奖励和一次材料消费。让工坊承担这一个真实功能即可。

**里程碑 C：可以交付。** 集中打磨这条路线的画面、音效、遭遇和撤离节奏；准备导出包和性能记录，再做陌生玩家试玩。

大地图、多个完整关卡、复杂制造树、完整基地经营、联机、程序生成都可以后排。Demo 目前最需要的是一条完整、清晰、有回报的体验。
