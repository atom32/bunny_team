## 玩家可做什么

Operations 原医疗携行面板现在同时显示当前装备使用的弹药类型。每种弹药可指定 0–1000 发，包括预装进弹匣的部分；默认三匣总量，不再把超出目标的整个弹药堆带走。两把同口径枪共用一个携行总量。偏好随存档保持，换枪后按新枪弹药类型显示。库存不足或容量不足时只装实际拥有且装得下的部分，下方预览显示实际数量和重量。

例如新档 120 发 5.56，选择 37：战斗开始为弹匣 30 + 备用 7，基地剩余 83。死亡只损失 37；打掉 5 发后成功撤离，仓库总量为 115，而不是 83、120 或 152。选择零确实带空枪，不赠送弹药。

## 部署事务 / 身份

1. 预览只计算，不修改仓库，也不创建持久化堆。
2. `DeploymentPlan.prepare` 在候选 profile 内拆分：基地余量保留原 ID；携行部分生成独立 ID。完整携行的原堆不另换 ID。
3. 使用候选启动 SortieSession，先将拆分后的仓库与初始 sortie checkpoint 一起原子保存，成功才发布。写盘失败清除临时 session，原仓库数量/ID/旧文件保持。
4. `Hanger._on_deploy_requested`（Hideout 的普通确认出击也走这里）使用 `DeploymentPlan.deploy`；不是只给测试场景加数量功能。
5. 结算继续按原 initial-carried-ID 集合移除/回收，所以不会误删基地余量。真实跨进程恢复后仍如此。挂起或未结算时禁止再次部署/修改携行。

`SortieRequest` 的原始 explicit-ID 接口仍表示“携行整个所指定实例”，用于已有 fixture/底层测试。`DeploymentPlan.carried_ids()` 仅提供源 ID，不能表达部分数量，已明确注释；精确生产路径必须使用 `prepare/deploy`。没有通过让同一个 ID 同时表示局内部分和基地余量来绕过结算。

schema 4 增加可选 `ammo_pack` 字典；旧档缺失表示默认计划，不补发物品。非法类型、未知弹药、负数、非整数/无穷和 >1000 拒绝加载。原有医疗、装备改装、武器/弹道/损伤和角色模型不变。

## 剩余边界

- 仅选择当前武器默认运行弹药的数量，没有在此偷偷加入弹匣物品/混装弹药/弹种切换系统。
- 自动装填与容量不足时的先后顺序沿用装备顺序，医疗仍按已有规则选择；预览明确实际携行。没有医疗与弹药自动优化器。
- 未证明三匣默认量、100kg 容量和改装成本具有正确长局平衡；需要多局真人试玩。
- 下一项是区域资源、重要地点与撤离选择，先检查已有区域/出口实现以免重复生产。完整 Alpha 仍包括设置、性能与约 10–15 次出击/2–4 小时的真实体验验证。
